## 轮3 审核新增项（P1 阻塞，本轮完成）

### 轮3 P1.1: 无效 preset fail-closed + 确定性测试 ✅

**问题：** `validate_all_preset_endpoints()` 只返回无效 preset ID 并记日志，审核方质疑"这些引擎已禁用"并不真实——所有翻译入口依旧直接调用 `providers::presets()`，无效 preset 仍可能被选择并发出请求。

**实现：**
- 拆出可注入的 `validate_preset_endpoints(list)` + 决策纯函数 `preset_gate_allows_client(invalid) -> bool`（任一无效 → false）。
- setup 中 `Ok(c) if preset_gate_allows_client(...) => Some(c)`，否则 `client = None`（fail-closed）。
- 所有翻译入口（`translate` / `translate_default` / `translate_clipboard` / `on_hotkey`）都经 `session_client()` 取 client；`client=None` 时返回错误并拒绝构建请求。

**测试（4 个，`lib.rs` 测试模块）：**
- `invalid_preset_in_catalog_blocks_client_gate`：伪 catalog 含 `ftp://` preset → 进入 invalid 列表 → 门关闭。
- `all_valid_presets_keep_client_gate_open`：正向对照。
- `session_client_refuses_when_client_disabled`：`client=None` → `session_client` 返回 Err（所有翻译入口的第一道屏障）。
- `session_client_returns_client_when_present`：正向对照。

> 说明：选择"存在无效 preset 即整体禁用 client"（审核给出的简单方案）而非 unified validated catalog——后者需要重写所有翻译入口的 preset 解析，范围超出本轮且 S2a 不触碰生产 `src/` 之外的前端。验证链是确定性的（无网络）：`validate_preset_endpoints` → `preset_gate_allows_client` → `session_client` 屏障，测试直接锁定每一环。

### 轮3 P1.2: 较低 schema_version 不得跳过迁移 ✅

**问题：** 只处理 `schema_version > SCHEMA_VERSION`；低版本 + `migration_complete=1` 会错误返回 `Complete`，未来 v1→v2 升级时旧 v1 库会跳过 v2 迁移。

**实现：** `migration_state_if_exists` 三分支：
```
schema_version > current  → Incompatible（硬停）
schema_version < current  → Incomplete（强制重跑迁移升级）
schema_version == current → 才检查 migration_complete
```
**测试（`db_schema.rs`）：** `lower_schema_version_with_complete_is_incomplete`、`future_schema_version_is_incompatible_even_when_complete`、`schema_version_read_propagates_sqlite_error_not_swallowed`、`current_schema_version_with_complete_reads_complete`。

### 轮3 P1.3: settings_path=None 时必须拒绝迁移 ✅

**问题：** 轮2 实现用 `settings_path.as_deref().unwrap_or(&empty_path)` 后继续跑迁移；空路径被当"settings 文件不存在"，可能继续迁移并标记完成，违背契约。

**实现：** 新增纯函数 `startup_migration_guard(settings_path: Option<&Path>, keystore_init_error) -> Result<&Path, String>`：
- `settings_path=None` → `Err`（拒绝迁移：不备份、不写库、不产生迁移状态）。
- keystore init 失败 → `Err`（迁移 Phase 1 需备份 keystore）。
- setup 中 guard 返回 Err 时跳过 `run_migration`，readiness 由 reducer 保持 `MigrationIncomplete "settings_path"` / `NeedsKeystoreRecovery`。

**测试（`startup_readiness.rs` 新增 5 个）：** 拒绝（None settings path）、拒绝（keystore 失败）、放行（健康路径原样返回）、`refused_guard_produces_no_backup_and_no_db_write`（全链证据：guard 拒绝时无 `.bak-pre-migration` 文件、DB 无迁移状态行）、guard 与 reducer 决策一致。

## 实际实现与计划差异

1. **原 Task 5d** 只要求"高于当前版本 → Incomplete"；轮3 审核升级为三分支语义（> → `Incompatible`、< → `Incomplete`），且 `<` 分支是审核发现的新 P1（轮3 P1.2）。
2. **原 Task 5a** `get_data_readiness` 从 String 改对象后，轮3 修正了注释（原先残留"wire format unchanged"的错误表述）。
3. **原计划 266 baseline** 已过时：最终为 **304 passed**（含本文件所列全部新增测试）。
4. **轮3 P1.1** 采用审核给出的"简单方案"（任一无效 preset → 整体禁用 client）并做了可测试性重构；未采用 validated catalog 方案（超出本轮范围，见上）。
5. **轮3 P1.3** 未新增测试用 `run_migration` 端到端执行（真实 Tauri setup 环境不可在单元测试中构造）；改为 `startup_migration_guard` 纯函数 + "guard 拒绝 ⇒ run_migration 不可达 ⇒ 无备份/无写库"的确定性证据测试，setup 中的调用路径与 guard 直接对应。
